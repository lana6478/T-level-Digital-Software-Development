# Employer Set Project

*Digital Software Development T Level → Core Component → Employer Set Project*

The Employer Set Project (ESP) is a substantial, externally set and marked assessment worth 40% of the core assessments (100 marks), taken over a combined duration of up to 14 hours 30 minutes across multiple sessions. It draws synoptically on knowledge and skills from across the whole core component, responding to a realistic vocational brief. Internet access and AI tools are not permitted during the assessed sessions. This page summarises the current specimen assessment material - the actual live assessment keeps the same overall number/focus of tasks, but the order and detail of tasks can change each series.

## Pre-task: familiarisation with the industry context

Not directly assessed and not taken under controlled conditions. Students investigate the context of the main brief (recent specimen material used the financial sector), working independently and in groups, to inform their responses to the assessed tasks.

## Task 1: Planning a project

Using a Pearson-provided template, students produce a project plan containing:

- **A Gantt chart** - assessing people's strengths/skills and assigning appropriate tasks, making scheduling decisions against a deadline, prioritising tasks based on requirements, assigning resources appropriately, and using a suitable software development lifecycle to organise tasks.
- **A resource and cost plan** - identifying and costing materials, physical resources and personnel; allocating resources and attributing costs for an accurate total project cost estimate; assessing a project's affordability and viability over time.
- **A rationale** - considering the most relevant planning factors and justifying notable decisions (task order/timing, team allocation, benefits/risks, impact on timings/costs).

## Task 2: Identifying and fixing defects in existing code

Students assess given code against requirements, test it to identify issues, and perform remedial action, justifying their fixes.

- **Documenting the testing process** - annotated evidence covering: tests to be carried out, the purpose of each test, test data used (valid, valid extreme, invalid, invalid extreme, erroneous), expected results, actual results, a comparison of the two, further actions needed, and refinement of the system.
- **The solution** - correcting errors and adding/removing code so the given code is functional and meets requirements, following programming conventions so the logic and structure are precise and outcomes consistently correct.

## Task 3: Designing a solution

- **Decomposition of the problem** - breaking the problem into computational parts, justifying decisions, using detailed abstraction/refinement, reusable components, and good decomposition to reveal every necessary sub-system, communicated with appropriate tools (flowcharts, code).
- **Application of logical thinking** - describing the solution's parts as algorithms with clearly and uniquely defined steps that depend on input and prior steps, using key constructs (sequence, selection, iteration).
- **Use of conventions** - correct structure/convention for the chosen communication method (correct flowchart symbols, correct code keywords), with consistent naming conventions throughout.
- **Communication of the design** - design documents detailed enough to communicate the intended solution, let the client make informed decisions, and let a third party build the proposed solution from them, using an appropriate mix of written/diagrammatic presentation, technical vocabulary, audience awareness, and explanations of structures/processes.

## Task 4a: Developing a solution

- **The solution** - applying programming knowledge to build a solution meeting the brief's requirements: refining the system, demonstrating technical skill and problem-solving, and using pre-written/user-written modules with an appropriate interface.
- **Code organisation** - avoiding sprawling nested if-clauses/loops with copy-pasted code, using clear meaningful indentation, precise logic via functions/classes/objects with proper structure, comments to explain logic, mostly local variables with minimal global use, constants, a well-designed interface, consistent style, defensive programming with secure data handling, and good exception handling.
- **User experience** - consistency, simplified input, meaningful output/error messages, and data visualisation (e.g. using Matplotlib for graphs showing trends/patterns).
- Note: formal testing documentation isn't required for this task, but students should still test their work, evidenced implicitly through a working product that meets the brief.

## Task 4b: Reflective evaluation

Applying reflection and evaluation techniques to provide evidence the product meets the brief: measuring against success criteria, evidencing from testing that it meets user needs, and discussing how it could be improved if revisited.

## What's assessed

The Employer Set Project's Assessment Objectives (see [Core scheme of assessment](04-core-scheme-of-assessment.md) for the full weighting breakdown) cover planning, applying knowledge/skills to develop software and fix defects, selecting relevant tools/techniques/resources, English/maths/digital skills, and realising and reviewing a project outcome.

## Key terms

- **Synoptic assessment** - assessment drawing together knowledge and skills from across the whole core component, rather than testing isolated topics.
- **Decomposition** - breaking a problem or solution down into smaller, manageable parts.
- **Defensive programming** - writing code that anticipates and safely handles unexpected inputs or conditions.
