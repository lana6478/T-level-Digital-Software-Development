# Testing a Software Solution

*Digital Software Development T Level → Occupational Specialism → Testing*

This is Content Area 7. It covers the types of testing a software solution needs, the techniques used to carry it out, and how to design good tests and test data.

## 7.1 Functional, non-functional and front-end testing

Students select and carry out the testing approach appropriate to the component being tested and the stage of the software development lifecycle it's at:

- **Functional testing** - unit testing, smoke testing, integration testing, system testing.
- **Non-functional testing** - availability testing, compatibility testing, configuration testing, load testing.
- **Front-end testing** - checking code/script performance and functionality, browser compatibility, operating system compatibility, cross-browser performance, formatting and rendering, loading times, and responsiveness.
- **Security testing** - vulnerability scanning, static analysis, dynamic analysis, integration analysis.

*(Signposted competencies: E1, E4, E5, E6, M2, M4, M5, M6, M8, M10, D1, D2, D4, D6.)*

## 7.2 Testing techniques

Students select appropriate manual and automatic testing techniques (including the use of AI tools) to check a software solution meets its identified requirements:

- **Acceptance testing** - does the software meet the client/user's requirements?
- **Alpha testing** - early-stage internal testing before release.
- **Beta testing** - testing with a limited group of real, external users before full release.
- **Closed box testing** - testing based only on inputs/outputs, without knowledge of the internal code (also called black box testing).
- **Open box testing / structural testing** - testing based on knowledge of the internal code structure (also called white box testing).

*(Signposted competencies: E1, E4, E5, E6, M2, M4, M5, M6, M8, M10, D1, D2, D4, D6.)*

## 7.3 Selecting tests and test data

To test a piece of functionality properly, students need to define:

- The **purpose** of the test.
- The **test data** to use, across several categories:
  - valid test data
  - invalid test data
  - valid extreme test data
  - invalid extreme test data
  - erroneous test data
- Any **pre-requisites** the test depends on.
- The **expected result**.

After running the test, the test plan should be updated with the actual results, any changes made as a result, and any re-tests or regression testing carried out following those changes.

*(Signposted competencies: E1, E4, E5, E6, M2, M4, M5, M6, M8, M10, D1, D2, D4, D6.)*

## Key terms

- **Regression testing** - re-running existing tests after a change, to make sure the change hasn't broken anything that used to work.
- **Black box / white box testing** - testing based only on external behaviour (black box) versus testing informed by the internal code structure (white box).
- **Extreme test data** - data right at the edge of what's valid or invalid, used to check boundary behaviour (e.g. the maximum allowed value, or one more than the maximum).
- **Erroneous test data** - data that's the wrong type or format entirely, used to check the system fails safely rather than crashing.
