# Change, Maintain and Support Software

*Digital Software Development T Level → Occupational Specialism → Change, Maintain and Support*

This is Content Area 8, the final technical content area of the specialism. It covers why software needs to keep changing after release, how to manage that change process, how to maintain code as part of a team, and how to support the people who actually use the software.

## 8.1 Why digital products change

Business-driven development shapes the type of maintenance a product needs:

- **Preventing** identified and foreseeable issues - e.g. changes to regulatory requirements, compatibility with new products/technology, changes in business process, or the release of a new product/service.
- **Correcting** unforeseen or previously unpreventable errors - e.g. new "zero day" vulnerabilities caused by changes elsewhere in the system, a targeted attack, data corruption, or system failures.
- **Iterating** to keep the product relevant - driven by user/client feedback, developments in technology, competition from other organisations, the need to improve efficiency, or the need to future-proof the product.

*(Signposted competencies: E1, E2, E3, E5, D3, D6.)*

## 8.2 The software change management process

Managing a change properly involves several stages:

1. Identify the issues/changes coming out of the feedback or review process.
2. Document the developments and changes made to the project.
3. Communicate with different audiences (technical and non-technical) about the change.
4. Plan the changes required.
5. Schedule the changes.
6. Carry out regression testing.
7. Control and release the updated product, whether the release is planned or reactive (e.g. an emergency fix).

*(Signposted competencies: E1, E2, E3, E5, M6, M10, D1, D3, D6.)*

## 8.3 Maintaining code as part of a larger team

Students need to understand and apply good coding principles when developing, adapting and maintaining code, working alongside other developers:

- Separating code and using modularity.
- Writing readable code.
- Using common/accepted coding conventions.
- Adding informative commenting/annotation within the code.
- Keeping change logs and other documentation up to date.

*(Signposted competencies: E1, E4, E5, E6, M2, M4, M5, M6, M8, M10, D1, D2, D3, D4, D6.)*

## 8.4 Supporting software users

**Communicating with users.** Students must be able to communicate with both technical and non-technical audiences, using the right tone and level of technical vocabulary, through:

- face-to-face communication
- remote conferencing
- written formats: blogs, formal reports, technical documentation, release notes, user guides/help files, FAQs
- visual and audio formats: user demonstrations, screencast videos, narration (recorded voice or text-to-speech)
- machine-readable API contracts

**Resolving issues.** Students apply a systematic process to support users and resolve their issues:

1. Identify or replicate the issue.
2. Investigate the possible cause - user error, system error, application error, or a security breach.
3. Apply testing techniques to identify the error in the system/code, make the necessary changes, confirm the error doesn't return, and confirm the fix hasn't caused any new issues.
4. Communicate how and when the issue was resolved to the appropriate stakeholders.
5. Document the lessons learned.

*(Signposted competencies: E1, E4, E5, E6, M2, M4, M5, M6, M8, M10, D1, D2, D3, D4, D6.)*

## Key terms

- **Zero-day vulnerability** - a security flaw that's exploited before a fix exists for it.
- **Regression testing** - re-testing existing functionality after a change to make sure nothing that used to work has broken.
- **Change log** - a running record of what's changed in a product and when, usually version by version.
